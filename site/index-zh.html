M5 · v1.0 准备 · Apache-2.0 · 离线优先

把一次历史故障，变成
可复现、可追溯、可评审的本地诊断报告。

kubectl-triage 是一个离线优先的 Kubernetes 事故诊断 CLI。 给一份脱敏的事故证据包，一条命令得到带证据引用、反证与缺失说明的 Markdown + JSON 报告——不接控制平面，不上传证据。 企业桥只提供 push 客户端与公开协议 1.0：显式配置端点/令牌， 默认只发报告与证据哈希。

5 分钟快速开始

从零到一份可评审的报告

安装、生成示例事故包、校验、分析、读报告。全程本地，不需要集群账号。

  1. 1

    安装 CLI

    go install github.com/paas-ops/kubectl-triage/cmd/kubectl-triage@latest
kubectl-triage version

    需要 Go 1.24+。预编译二进制、Docker、Homebrew 见安装矩阵。

  2. 2

    生成示例事故包

    kubectl-triage init /tmp/triage-demo

    生成 incident.yaml、k8s/events.json、logs/app.log、metrics/memory.json。

  3. 3

    校验事故包

    kubectl-triage validate /tmp/triage-demo

    JSON Schema、RFC3339 时间戳与敏感内容扫描；命中凭据类内容默认退出码 4。

  4. 4

    本地诊断

    kubectl-triage analyze /tmp/triage-demo

    默认离线规则，30 秒内出结果；报告写入包内 report.md / report.json。

  5. 5

    读报告

    report.md：摘要 → 证据时间线 → 候选根因（含反证与置信）→ 缺失证据 → 只读修复建议。report.json 接入工单 / 知识库。

也可以作为 kubectl 插件

kubectl triage analyze /tmp/triage-demo

二进制名为 kubectl-triage（Windows 为 kubectl-triage.exe）且在 PATH 中时，kubectl 会自动发现它。

稳定退出码（CI 可用）

analyze 退出码
0成功，报告已生成
1输入 / 配置错误
2--fail-on-missing 触发
3模型失败，已降级离线（报告 degraded: true）
4安全校验失败（疑似 Secret / 越权数据）

方式 命令 / 产物 状态

离线与安全

默认不联网，只读，模型与 push opt-in

安全 / 合规评审可以把这份边界当作验收清单；数据流与权限清单见文档。

默认零网络

不传 --model 时不发起任何网络请求；--offline 是硬保证，与模型模式互斥。

只读

不调用 Kubernetes 写接口，不 exec / apply / delete，不读取 Secret；只消费本地事故包，报告只写本地。

模型 / push opt-in

模型与 enterprise push 都需显式启用：模型只访问 --model-url；push 只访问 --endpoint，默认只发报告与证据哈希。两者都禁用重定向。

遥测默认关闭

不发送任何数据。启用后只上报白名单字段（版本 / OS / 架构 / 故障类目 / 耗时等），绝不采集事故内容。

本地 eval

把诊断质量变成可回归的数字

对 golden 事故包做确定性评测；模型模式可对比不同 provider / 模型。

# 复现仓库内 12 个 golden（固定时钟保证确定性）
kubectl-triage eval testdata/golden --now 2026-10-30T14:00:00Z

# 机器可读结果（稳定 JSON 契约，CI 用）
kubectl-triage eval testdata/golden --now 2026-10-30T14:00:00Z --json

# 对同一组用例评测模型模式
kubectl-triage eval testdata/golden --now 2026-10-30T14:00:00Z \
  --model ollama --model-name llama3.1

企业试点

用你脱敏的历史事故检验它

开源 CLI 永远可以完成一次完整诊断，不限次数；试点面向团队化能力： 团队事故库、评测集管理、审计与私有化部署。提交申请后用 28 天一起验证真实事故上的可用性。

  • 团队 ≥2 名 SRE / 平台工程师，≥3 个集群
  • 有 Prometheus / Alertmanager，能提供 ≥10 起脱敏历史事故
  • 有团队事故库 / 审计 / 私有部署需求之一
  • 接受 28 天试点与验收口径
