Turn a past incident into a
reproducible, traceable and reviewable local diagnosis report.

kubectl-triage is an offline-first Kubernetes incident triage CLI. Give it a redacted incident bundle and one command produces a Markdown + JSON report with evidence citations, contradictions and missing-evidence notes — no control plane, no evidence upload. The enterprise bridge ships only a push client and the public protocol 1.0: explicitly configured endpoint and token, sending the report and evidence hashes by default.

5-minute quickstart

From zero to a reviewable report

Install, create a sample incident bundle, validate, analyze, read the report. Everything stays local; no cluster account required.

  1. 1

    Install the CLI

    go install github.com/paas-ops/kubectl-triage/cmd/kubectl-triage@latest
kubectl-triage version

    Requires Go 1.24+. Prebuilt binaries, Docker and Homebrew: see the install matrix.

  2. 2

    Create a sample incident bundle

    kubectl-triage init /tmp/triage-demo

    Creates incident.yaml, k8s/events.json, logs/app.log and metrics/memory.json.

  3. 3

    Validate the bundle

    kubectl-triage validate /tmp/triage-demo

    JSON Schema, RFC3339 timestamps and sensitive-content scanning; credential-like content exits with code 4 by default.

  4. 4

    Analyze locally

    kubectl-triage analyze /tmp/triage-demo

    Deterministic offline rules, done in under 30 seconds; writes report.md / report.json into the bundle.

  5. 5

    Read the report

    report.md: summary → evidence timeline → candidate root causes (with contradictions and confidence) → missing evidence → read-only remediation advice. Plug report.json into your ticketing or knowledge base.

Use it as a kubectl plugin

kubectl triage analyze /tmp/triage-demo

When a binary named kubectl-triage (kubectl-triage.exe on Windows) is on PATH, kubectl discovers it automatically.

Stable exit codes (CI-friendly)

analyze exit codes
0Success, report written
1Input / configuration error
2--fail-on-missing triggered
3Model failure, degraded to offline rules (report has degraded: true)
4Security validation failed (suspected Secret / unauthorized data)

Offline & security

Offline by default, read-only, model and push opt-in

Security and compliance reviews can use this boundary as a checklist; data flow and permission inventory are in the docs.

Zero network by default

Without --model the CLI makes no network requests; --offline is a hard guarantee and is mutually exclusive with model mode.

Read-only

No Kubernetes write APIs, no exec / apply / delete, no Secret reads; it only consumes the local incident bundle and writes reports locally.

Model / push opt-in

Both model and enterprise push require explicit opt-in: the model only reaches --model-url; push only reaches --endpoint and sends the report plus evidence hashes by default. Both disable redirects.

Telemetry off by default

Nothing is sent. When enabled, only whitelisted fields are reported (version / OS / arch / fault class / duration, etc.); incident content is never collected.

Local evaluation

Turn diagnosis quality into a regression number

Deterministic evaluation over golden incident bundles; model mode can compare providers and models.

# Reproduce the 12 golden cases in the repo (fixed clock for determinism)
kubectl-triage eval testdata/golden --now 2026-10-30T14:00:00Z

# Machine-readable result (stable JSON contract, for CI)
kubectl-triage eval testdata/golden --now 2026-10-30T14:00:00Z --json

# Evaluate model mode over the same set
kubectl-triage eval testdata/golden --now 2026-10-30T14:00:00Z   --model ollama --model-name llama3.1

Scoring signals

  • Top1
  • Top3
  • Missing handling
  • Injection safety
  • Degraded count
  • Error count

Exit codes

0 all pass · 1 input/config error · 2 failing cases

The offline rules’ 12/12 is a deterministic regression, not statistical accuracy; the formal 100-case blind set is managed separately as an enterprise / release gate.

Enterprise pilot

Test it with your own redacted incidents

The open-source CLI can always complete a full diagnosis, with no usage limits; the pilot focuses on team capabilities: a team incident library, evaluation set management, audit and private deployment. Apply, then spend 28 days validating it on real incidents.

  • Team of ≥2 SREs / platform engineers, ≥3 clusters
  • Prometheus / Alertmanager available and ≥10 redacted historical incidents
  • A need for a team incident library, audit or private deployment
  • Acceptance of the 28-day pilot and its acceptance criteria

Enterprise bridge (push): OSS ships only the client and public protocol 1.0; the receiving side and team capabilities come from the commercial edition. Push protocol · OSS vs Enterprise
