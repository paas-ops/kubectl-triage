kubectl-triage 项目文档

版本 v0.5.0 · 2026-10-30 · Apache-2.0 · https://github.com/paas-ops/kubectl-triage

本文档是项目的综合说明与事实源入口：定位、架构、数据契约、命令、安全、质量、里程碑与路线图。详细口径以各链接文档与 ADR 为准。

1. 项目定位

kubectl-triage 是一个轻量、离线优先的 Kubernetes 事故诊断 CLI：开发者拿到一份脱敏的事故证据包，在本地执行一条命令，得到一份可复现、可追溯、可评审的 Markdown/JSON 诊断报告——不依赖控制平面、不上传生产证据、不要求账号。

产品承诺：

  • 5 分钟内完成第一次本地诊断：无账号、无登录、无云端依赖，init 生成可跑通示例；
  • 历史事故可复盘：证据包可存档、可分享、可回归（golden + 本地 eval）；
  • 可信度来自证据：每条结论引用证据，并给出反证、缺失说明与置信分层，而不是模型口吻；
  • 默认安全：默认零网络、只读、不读 Secret；模型与推送均为显式 opt-in。

2. 目标用户与典型场景

用户场景成功标准
应用开发者收到告警，本地只有 kubectl 输出和几段日志不登平台即得到有证据的根因草稿
值班 SRE事故后复盘，需要证据与结论留档一份可审阅的 Markdown/JSON 报告
平台工程师评估诊断工具是否值得团队采购用自己脱敏的历史事故复跑与评测
安全/合规生产日志不能出域离线模式运行、证据哈希可核验
企业购买者团队需要事故库、评测与审计从 CLI 试点升级到企业版

开源 CLI 免费做“一次、本地、单事故”的诊断；企业版卖“团队、评测、审计、私有化”。

能力开源 CLI（免费）企业版（CloudOps Agent）

审计（谁在何时看了什么、模型/版本）❌✅
SSO/RBAC/多租户/私有部署/SLA❌✅

4. 核心概念

概念说明
事故包（bundle）一个目录：incident.yaml + 证据（k8s/metrics/logs/changes/alert.json）；本地、可存档
证据（evidence）规范化条目：id / source / observed_at / collected_at / summary / content_ref / sha256 / stale
报告（report）report.json（schema_version 1.0，稳定接口）+ 由其渲染的 report.md
假设（hypothesis）最多 3 条，按置信排序；每条 ≥1 条有效证据；可带反证与缺失说明
评测集（eval set）与事故包同构的用例集合 + expected/report.json；golden 与正式 100 例共用契约
企业推送（push）显式配置的客户端：默认只发报告 + 证据哈希，可选脱敏证据包；协议 v1.0 公开

5.2 数据流

事故包目录 ──► bundle(Load/Validate, redact) ──► evidence(规范化/裁剪)
                                              │
                                              ├─► rule 引擎（五类规则）──► 报告（离线）
                                              └─► model(可选) ── 校验/中和 ──► 报告（增强/降级）
报告 ◄──────────────────────────────────────────┘
  ├─► report.md / report.json（本地）
  ├─► eval（与 expected 对比：Top1/Top3/缺失/注入/降级）
  └─► push（显式配置；报告+证据哈希，可选证据包）

7. 数据契约

7.1 事故包（输入）

incident.yaml 必填字段：id, alertname, severity(critical|warning|info), cluster, namespace, workload, observed_at, collected_at, source（RFC3339 时间）。

证据文件（可选，按需）：alert.json、k8s/events.json、k8s/pods.yaml、k8s/deployments.yaml、metrics/*.json、logs/*.log、changes/rollout.json、runbook.md、notes.md。

7.2 报告（输出）

顶层字段：schema_version("1.0"), incident, generated_at, mode(offline|model), degraded, summary, evidence[], hypotheses[≤3], missing_data[], recommended_checks[], suggested_fix, limitations[], versions{}。

  • 证据字段：id, source, observed_at, collected_at, summary, content_ref, query?, redaction?, sha256, stale, skew_seconds?；
  • content_ref 约定：整文件 <rel>、JSON 条目 <rel>#items/<n>、日志行<rel>#L<n>；
  • 每条结论必须引用存在证据；反证与支持证据不得同 id；建议均为只读、不生成可执行脚本。

7.3 版本与兼容

  • 报告 schema_version 固定 1.0；v0.x 允许破坏性变更但需 CHANGELOG + 迁移说明；
  • v1.0 起至少兼容一个大版本；新增可选字段不破坏旧消费者（策略见 schema 契约 与ADR-007）；
  • 兼容性由 pkg/schema 基线测试守护（UPDATE_COMPAT=1 显式变更 + review）。

8. 分析引擎

8.1 五类故障规则（确定性，rule-v0.2）

故障类典型信号默认置信
OOMKilledOOMKilled、exitCode=137、内存 limit 相关high（≥2 独立来源且新鲜）
CrashLoopBackOffCrashLoopBackOff、Back-off restartingmid
ImagePullBackOffErrImagePull、pull access denied、manifest unknownhigh
PendingFailedScheduling、资源不足/亲和性mid
发布回归changes/ 记录 + ReplicaSet/镜像差异mid/low

每个假设带：证据引用、反证（如镜像曾成功拉取、探针失败、发布早于故障窗口）、置信分层（high/mid/low，stale/反证会降级）、缺失证据与下一步、只读修复建议。

8.2 可选模型（默认关闭）

  • provider：OpenAI-compatible（/v1/chat/completions）/ Ollama（/api/chat）；温度 0、仅 JSON；
  • 只访问配置端点、禁用重定向；证据视为不可信数据；模型输出经 schema + 引用闭合 + 文本中和；
  • 预算/超时/轮次受控（默认 $1 / 60s / 3 轮）；任何运行时失败保留离线报告并标 degraded，退出码 3；配置错误退出码 1。详见 模型模式。

9. 安全与隐私

  • 默认离线：不访问集群、不访问网络；模型、push、遥测均显式 opt-in；
  • 只读：不读 Secret、不解析 kubeconfig、不执行 exec/apply/delete；修复建议均只读；
  • 输入安全：导入/校验/推送前扫描凭据模式；报告不回显密钥；越权/越界证据引用拒绝；
  • 注入防护：证据中“忽略指令/执行命令/外传”类文本不执行、不进入报告，模型输出二次中和；
  • 遥测默认关闭：仅 10 个白名单字段（版本/OS/架构/模式/耗时/证据条数等），绝不采集集群、命名空间、日志、证据正文、路径、密钥；KUBECTL_TRIAGE_TELEMETRY=off 强制关闭；
  • 供应链：Release 提供 sha256 + cosign keyless 签名 + CycloneDX SBOM；GHCR 镜像按 digest 签名。

详见 安全与数据流。

13. 指标与运营

北极星不是 Star，而是四层漏斗：

  1. 实际安装：Release 下载 / Homebrew analytics / GHCR 拉取（去重）；
  2. 激活：opt-in analyze 事件（首次成功生成报告）；
  3. 重复使用：激活后 4 周内 ≥2 次成功诊断（install_id 去重）；
  4. 企业试点：合格申请 ≥10、进入试点 ≥3、转正/付费（90 天商业门槛）。

当前状态：工具链已就绪（遥测客户端、试点 issue 表单、playbook、周报模板），真实数字依赖对外发布与运营（截至 v0.5.0 尚未开始外部推广）。定义与周报模板见 指标漏斗。
