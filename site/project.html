1. Project Positioning

kubectl-triage is a lightweight, offline-first Kubernetes incident triage CLI: a developer takes a redacted incident evidence bundle, runs a single command locally, and gets a reproducible, traceable and reviewable Markdown/JSON diagnosis report — without a control plane, without uploading production evidence, and without an account.

Product promises:

  • First local diagnosis in under 5 minutes: no account, no login, no cloud dependency; init generates a runnable example;
  • Historical incidents can be reviewed: bundles are archivable, shareable and replayable (golden + local eval);
  • Credibility comes from evidence: every conclusion cites evidence and shows counter-evidence, missing-data notes and confidence tiers instead of model rhetoric;
  • Secure by default: zero network, read-only, never reads Secrets; model and push are explicit opt-in.

7. Data Contracts

7.1 Incident Bundle (input)

Required incident.yaml fields: id, alertname, severity(critical|warning|info), cluster, namespace, workload, observed_at, collected_at, source (RFC3339 timestamps).

Optional evidence files (as needed): alert.json, k8s/events.json, k8s/pods.yaml, k8s/deployments.yaml, metrics/*.json, logs/*.log, changes/rollout.json, runbook.md, notes.md.

7.2 Report (output)

Top-level fields: schema_version("1.0"), incident, generated_at, mode(offline|model), degraded, summary, evidence[], hypotheses[≤3], missing_data[], recommended_checks[], suggested_fix, limitations[], versions{}.

  • Evidence fields: id, source, observed_at, collected_at, summary, content_ref, query?, redaction?, sha256, stale, skew_seconds?;
  • content_ref conventions: whole file <rel>, JSON entry <rel>#items/<n>, log line <rel>#L<n>;
  • Every conclusion must cite existing evidence; counter-evidence and supporting evidence must not share the same id; all suggestions are read-only and never generate executable scripts.

7.3 Versioning and Compatibility

  • The report schema_version is fixed at 1.0; v0.x allows breaking changes but requires a CHANGELOG + migration notes;
  • Starting with v1.0, at least one major version is supported; new optional fields do not break old consumers (see the schema contract (Chinese) and ADR-007 (Chinese));
  • Compatibility is guarded by the pkg/schema baseline tests (UPDATE_COMPAT=1 for explicit changes + review).

8. Analysis Engine

8.1 Five Failure-Class Rules (deterministic, rule-v0.2)

Failure classTypical signalsDefault confidence
OOMKilledOOMKilled, exitCode=137, memory-limit relatedhigh (≥2 independent sources and fresh)
CrashLoopBackOffCrashLoopBackOff, Back-off restartingmid
ImagePullBackOffErrImagePull, pull access denied, manifest unknownhigh
PendingFailedScheduling, insufficient resources/affinitymid
Release regressionchanges/ records + ReplicaSet/image diffmid/low

Each hypothesis carries: evidence citations, counter-evidence (for example the image was pulled successfully earlier, probe failures, a rollout earlier than the incident window), confidence tiers (high/mid/low; stale evidence or counter-evidence lowers it), missing evidence and next steps, and read-only remediation suggestions.

8.2 Optional Model (disabled by default)

  • providers: OpenAI-compatible (/v1/chat/completions) / Ollama (/api/chat); temperature 0, JSON only;
  • only the configured endpoint is contacted; redirects are disabled; evidence is treated as untrusted data; model output goes through schema validation, citation closure and text neutralization;
  • budget/timeout/rounds are controlled (defaults $1 / 60s / 3 rounds); any runtime failure keeps the offline report and marks it degraded, exit code 3; configuration errors exit code 1. See Model mode (Chinese).

9. Security and Privacy

  • Offline by default: no cluster or network access; model, push and telemetry are all explicit opt-in;
  • Read-only: never reads Secrets, never parses kubeconfig, never executes exec/apply/delete; all remediation suggestions are read-only;
  • Input safety: credential patterns are scanned before import/validation/push; reports never echo keys; out-of-scope/out-of-bounds evidence references are rejected;
  • Injection protection: text in evidence that says "ignore instructions / execute commands / exfiltrate" is neither executed nor copied into reports, and model output is neutralized again;
  • Telemetry off by default: only 10 allowlisted fields (version/OS/architecture/mode/duration/ evidence count, etc.); cluster, namespace, logs, evidence bodies, paths and keys are never collected; KUBECTL_TRIAGE_TELEMETRY=off forces it off;
  • Supply chain: releases provide sha256 + cosign keyless signatures + CycloneDX SBOMs; GHCR images are signed by digest.

See Security and data flow (Chinese) for details.

13. Metrics and Operations

The north star is not GitHub Stars but a four-stage funnel:

  1. Actual installs: Release downloads / Homebrew analytics / GHCR pulls (deduplicated);
  2. Activation: opt-in analyze event (first successful report generation);
  3. Repeat usage: at least 2 successful diagnoses within 4 weeks after activation (deduplicated by install_id);
  4. Enterprise pilots: ≥10 qualified applications, ≥3 entering a pilot, conversion/payment (the 90-day commercial threshold).

Current status: the tooling is ready (telemetry client, pilot issue form, playbook, weekly report template), but real numbers depend on external release and operations (as of v0.5.0, external promotion has not started yet). Definitions and the weekly report template are in Metrics funnel (Chinese).
