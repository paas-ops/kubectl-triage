# 企业试点运营手册（28 天）

面向 **试点客户对接人 + 维护者/商业团队** 的可执行手册：把“申请 → 安装 → 首批事故回放 →
评测/审计验收 → 复盘”固定成 28 天节奏。资格与申请入口见 [企业试点指南](pilot.md)，
指标口径见 [指标漏斗与周报](metrics.md)，OSS/企业版边界见 [开源版与企业版](enterprise.md)。

> 原则：**用客户脱敏的真实历史事故验证价值**，不靠演示；试点期间不收集事故内容以外的数据；
> 开源 CLI 始终可独立完成单次诊断，试点只是在此基础上验证团队化能力。

## 适用对象与角色

| 角色 | 由谁担任 | 职责 |
| --- | --- | --- |
| 客户对接人 | 客户 SRE / 平台负责人 | 排期、组织评审、确认数据边界与验收 |
| 客户 SRE 评审 | 2–3 名值班/平台工程师 | 提供脱敏事故、阅读报告并评分、反馈缺口 |
| 维护者（OSS） | 项目维护者 | 安装支持、问题定位、协议/客户端答疑 |
| 商业团队 | CloudOps Agent | 企业能力（事故库/评测/审计/私有化）交付与商务 |
| 安全/合规（如需） | 客户安全团队 | 审查数据流、令牌与远程访问边界 |

## 试点资格

与[拆分计划 §6.3](拆分计划.md)一致（不满足也可以先用开源版）：

- 团队 **≥2 名** SRE / 平台工程师，**≥3 个**集群；
- 有 Prometheus / Alertmanager，能提供 **≥10 起**脱敏历史事故；
- 有团队事故库 / 审计 / 私有部署需求**之一**；
- 接受 **28 天试点**与验收口径。

## 28 天时间线

| 阶段 | 时间 | 里程碑 | 产出 / 验收证据 |
| --- | --- | --- | --- |
| 准备 | D-7 ~ D0 | 申请 → 资格访谈 → 签收试点范围 | 试点协议/范围邮件、数据脱敏规范、对接人与排期 |
| 安装与首次成功 | D1 ~ D3 | 安装 CLI，跑通 `init → validate → analyze` 与（可选）模型 | 首份 `report.md`、安装方式与版本记录、阻塞清单 |
| 首批事故回放 | D4 ~ D10 | 先 2–3 起校准流程，再完成 **≥10 起**事故 | 事故包与报告清单、每起 `report.json`、耗时记录 |
| 评测与质量 | D11 ~ D17 | 本地 eval 回归 + 客户评测集（如提供）；模型模式可选对比 | eval 结果、模型/离线对比、缺口与误判清单 |
| 团队化验证 | D18 ~ D21 | 按签收范围验证企业能力；如需签名推送，先 `--dry-run` 再内网联调 | 企业能力验收记录；push 幂等/审计验证记录（可选） |
| 复盘与验收 | D22 ~ D28 | 验收评分会 + 复盘 + 决策 | 验收表、复盘文档、是否转正/继续试点的结论 |

### D-7 ~ D0：准备

- 通过 [Issue 表单](https://github.com/paas-ops/kubectl-triage/issues/new?template=pilot-request.yml)
  提交申请（字段见 [.github/ISSUE_TEMPLATE/pilot-request.yml](../.github/ISSUE_TEMPLATE/pilot-request.yml)）；
- 30 分钟资格访谈：事故类型、数据出域限制、目标能力、成功标准；
- 签收试点范围：验证哪 1–2 个团队化能力、验收口径、数据留存方式；
- 明确**只提供脱敏数据**；若需要 `push`，确认企业控制平面端点与令牌由客户内网管理。

### D1 ~ D3：安装与首次成功

- 按客户环境选择安装方式（[安装与校验](install.md)），记录版本与平台；
- 跑通 [5 分钟快速开始](quickstart.md)；
- 遥测保持默认关闭；若客户愿意启用，先走 [安全与数据流](security.md#遥测隐私默认关闭) 评审；
- 输出：首份报告的团队评审意见（格式、证据引用、可读性）。

### D4 ~ D10：首批事故回放（≥10 起）

- 分批导入：先 2–3 起校准事故包结构与脱敏规范，再批量到 ≥10 起；
- 覆盖建议：至少 2–3 类（OOMKilled / CrashLoopBackOff / ImagePullBackOff / Pending / 发布回归）；
- 每起记录：事故包路径（内部编号即可）、CLI 版本、模式（offline/model）、退出码、耗时、报告结论；
- **不要**把事故内容、日志或集群标识贴到 GitHub issue；问题用最小复现描述。

### D11 ~ D17：评测与质量

- 跑本地确定性回归：`kubectl-triage eval testdata/golden --now <固定时间>`（安装验证）；
- 客户有评测集时，按 [评测集契约](eval-contract.md) 评估；企业侧可做版本对比与盲测；
- 模型模式可选：对比 offline vs 模型模式 Top1/Top3、耗时与成本，注意预算（[模型模式](model.md)）；
- 输出：质量结论仅作试点验收依据，**不对外宣传为统计准确率**。

### D18 ~ D21：团队化验证

- 按签收范围验证企业能力：团队事故库/检索/标签、评测集管理、审计、SSO/RBAC、私有化等；
- 若试点包含 `push`：
  1. 先 `kubectl-triage push <dir> --endpoint <内网地址> --dry-run --out /tmp/payload.json`，
     人工检查 payload 摘要与（默认不含）证据正文；
  2. 只用客户内网/loopback 端点联调，令牌放在环境变量，不写进脚本或日志；
  3. 验证幂等：同一报告重复推送（相同 `push_id`/Idempotency-Key 在重试内复用）不产生重复事故；
  4. 需要证据包时由客户书面确认后再加 `--include-evidence`，并记录上传大小与哈希；
  5. 协议细节见 [Push 协议 1.0](push-protocol.md)。

### D22 ~ D28：复盘与验收

- 按下方“验收口径”逐项打分，形成验收表；
- 复盘会 60 分钟：结果、缺口、是否进入商业合作；
- 输出：验收表 + 复盘文档 + 决策（转正 / 继续试点 / 暂缓）。

## 每周节奏

| 时间 | 事项 | 时长 |
| --- | --- | --- |
| 周一 | 指标与进度同步：本周事故数、阻塞、数据边界、下周排期 | 15–30 min |
| 周三 | 客户 SRE 评审 2–3 份报告，记录可用性评分与缺口 | 30 min |
| 周五 | 维护者侧问题收敛、文档/客户端修复、周报更新 | 30 min |

周报模板见 [指标漏斗与周报](metrics.md#周报模板)。

## 验收口径

| 维度 | 建议目标 | 证据 | 负责人 |
| --- | --- | --- | --- |
| 诊断覆盖 | ≥10 起脱敏事故完成完整流程，覆盖 2–3 类故障 | 事故包 + 报告清单 | 客户对接人 |
| 报告可用性 | 客户 SRE 评分 ≥4/5（1–5），记录评分分布 | 评分表 | 客户评审 |
| 性能 | 离线分析 ≤30s / 单次模型运行 ≤5 min | CLI 耗时记录 | 维护者 |
| 安全 | 零敏感泄漏、零未授权外传 | 脱敏/注入负例、网络审计 | 双方安全 |
| 重复使用 | 试点期内同一团队多次主动使用 | 使用记录（不含事故内容） | 客户对接人 |
| 团队化能力 | 签收范围内的 1–2 项能力完成场景验证 | 能力验收记录 | 商业团队 |

> 开源本地 eval 的 12/12 是**确定性回归**，不是统计准确率；正式质量结论以试点签收与企业评测为准。

## 数据边界与脱敏流程

1. **客户先脱敏**：只提供脱敏事故包；不提供 Secret、完整环境变量、客户数据正文；
2. **CLI 再扫描**：`validate` / `import` 以 `--redact strict` 扫描敏感模式，命中退出 4；它是
   尽力而为的启发式规则，不替代客户脱敏流程；
3. **默认不传证据**：`push` 默认只发送报告与证据哈希；证据正文仅在显式 `--include-evidence`
   时上传，且需客户书面确认；
4. **令牌边界**：`KUBECTL_TRIAGE_ENTERPRISE_TOKEN` 只从环境变量读取，不写入报告/日志/错误信息，
   由客户内网管理；
5. **不要外泄**：issue、聊天、截图中不出现事故正文、集群名、令牌；问题用合成/最小复现；
6. **数据处理**：试点数据的存储、保留、删除在试点协议中约定；仓库文档不构成商业条款。

## 风险与红线

| 风险 | 应对 |
| --- | --- |
| 误传真实数据 | 只收脱敏数据；`--include-evidence` 需书面确认；先 `--dry-run` |
| 把 OSS 当免费企业版 | 明确 [企业边界](enterprise.md)；团队库/审计/评测不在 OSS |
| 承诺未实现功能 | 只承诺已发布能力；企业能力以商业团队签收为准 |
| 范围蔓延 | 以签收的 1–2 项能力与验收表为准，其余进 backlog |
| 无对接人/节奏失守 | D0 指定对接人，周一同步固定进日历 |
| 指标失真 | 按 [指标口径](metrics.md) 记录来源与局限，不以 Star 为 KPI |
