# kubectl-triage 拆分计划

**从 CloudOps Agent 拆出一个独立开源 CLI，用 12 周做出可安装、可重复使用、能带来企业试点的 v0.1**

| 项 | 内容 |
| --- | --- |
| 版本 | v0.1（执行稿） |
| 日期 | 2026-10-30 |
| 关联 | [需求文档](需求文档.md)、[创业商业方案](../../CloudOps-Agent/创业商业方案.md)（外部商业仓库，不随本仓库发布） |
| 目标 | 90 天内：可安装 CLI + 真实使用 + ≥10 个合格企业试点请求 |
| 团队 | 1 Go/CLI、1 平台后端、0.5 设计/文档、SRE 顾问、创始人 GTM |

## 一 拆分原则

1. **独立仓库、独立发布**：`kubectl-triage` 不跟随 CloudOps Agent 的发布节奏；CLI 可以每周发版。
2. **不复制企业代码**：只抽取公开的证据/报告 schema 与五类故障规则；企业 runbook、租户、审计、
   SSO、评测服务不进入开源仓库。
3. **开源版可独立完成一次诊断**：不依赖控制平面、不强制登录、不强制遥测。
4. **企业版是“团队化”而不是“解锁单次诊断”**：团队事故库、评测、审计、私有部署在
   CloudOps Agent 侧实现；CLI 只保留一个显式的 `push` 客户端。
5. **指标先行**：从第一天记录安装、激活、重复使用、试点请求；Star 只做参考。

### 1.1 拆分后的两个产品面

```text
┌─────────────────────────────┐        ┌──────────────────────────────┐
│ kubectl-triage（Apache-2.0）│        │ CloudOps Agent（商业版）      │
│ 单二进制 / 本地 / 单事故     │  push  │ 团队事故库 / 评测 / 审计      │
│ 离线规则 / 可选模型          │ ─────► │ SSO / RBAC / 私有部署 / SLA   │
│ Markdown + JSON 报告         │  opt-in│ 多租户控制平面 + Web 控制台   │
└─────────────────────────────┘        └──────────────────────────────┘
```

共享的只有 **schema 与报告格式**；不共享数据库、租户模型、企业策略。

### 2.1 仓库

- 工作名：`kubectl-triage`
- 已确认 module：`github.com/paas-ops/kubectl-triage`（仓库：https://github.com/paas-ops/kubectl-triage）

│   └── telemetry/               # opt-in 匿名事件（默认关闭）

├── testdata/golden/             # 脱敏事故包 + 期望报告
├── examples/                    # 5 分钟示例
├── docs/                        # 安装、导入、安全、评测、贡献

### 2.3 技术选择

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | Go 1.24+（CI 用 1.26） | 单二进制、K8s 生态、跨平台交叉编译 |
| CLI | `spf13/cobra` | 子命令/补全/帮助成熟 |
| 配置 | YAML + 环境变量 + flags | 本地优先，无服务端配置中心 |
| 输出 | JSON Schema + Markdown | 机器可读 + 人可读 |
| 模型 | OpenAI-compatible / Ollama | 不绑定供应商；本地模型可离线 |
| 打包 | GoReleaser + Homebrew tap + GHCR | 安装路径短，便于统计下载 |
| 测试 | `go test` + golden + schema | 确定性规则可回归 |
| 遥测 | 自建 opt-in HTTP（匿名） | 不引入第三方 SDK，数据最小化 |

## 三 12 周里程碑

> 以 2026-11-02 为 W1；与商业方案 90 天窗口对齐。W12 后进入企业试点。

| 阶段 | 时间 | 交付 | 退出条件 |
| --- | --- | --- | --- |

- 周一：指标复盘（安装/激活/重复/试点）+ 本周范围；

- 周五：发布候选/文档更新；每两周一次对外 demo。

## 五 发布与质量门禁

### 5.1 每次 PR

- `go test ./...`、`go vet ./...`、`golangci-lint`（或等价）
- golden 报告对比（确定性）
- schema 校验
- 脱敏/注入负例
- 构建矩阵（darwin/linux × amd64/arm64）

### 5.2 发布门禁

| 门禁 | 条件 |
| --- | --- |
| Alpha（W4） | 12 golden 通过；离线 <30s；示例可跑 |
| Beta（W8） | 安装包可用；零敏感泄漏；模型降级；文档完整 |
| v0.1（W12） | 100 安装/30 激活/5 试点沟通；≥10 合格试点请求；安全审查通过 |
| 企业试点 | 客户提供 ≥10 起脱敏事故；验收口径签收 |

### 5.3 版本与兼容

- CLI SemVer；`report.json` 有 `schema_version`；
- `v0.x` 允许破坏性变更但需 `CHANGELOG` + 迁移说明；
- `v1.0` 后 schema 至少兼容一个大版本；
- 规则版本独立于 CLI 版本，报告中记录。

## 六 指标与埋点计划

### 6.1 数据最小化

默认 **不发送任何数据**。首次运行时询问是否开启匿名统计；也可 `--telemetry=off`。
事件只含：

```json
{
  "install_id": "random-uuid",
  "event": "analyze_success",
  "version": "0.1.0",
  "os": "darwin",
  "arch": "arm64",
  "mode": "offline|model",
  "fault_class": "OOMKilled",
  "duration_ms": 1200,
  "evidence_count": 18,
  "outcome": "ok|missing|error"
}
```

**绝不采集**：集群名、命名空间、告警名、日志、证据正文、模型 key、文件路径。

### 6.2 指标看板（每周）

| 指标 | 来源 | 目标（90 天） |
| --- | --- | --- |
| Release 下载 | GitHub API | ≥1,000 |
| Homebrew 安装 | Homebrew analytics（若启用） | 参考 |
| 容器拉取 | GHCR | 参考 |
| 激活 | opt-in `first_success` | ≥30% 安装 |
| 4 周重复 | opt-in `analyze_success` 去重 | ≥25% 激活 |
| 企业试点请求 | 表单 UTM + 资格访谈 | ≥10 |
| 进入试点 | CRM | ≥3 |
| Star | GitHub | 只记录，不设目标 |

### 6.3 试点请求资格

- 团队 ≥2 名 SRE/平台工程师，≥3 集群；
- 有 Prometheus/Alertmanager，能提供 ≥10 起脱敏历史事故；
- 有团队事故库/审计/私有部署需求之一；
- 接受 28 天试点与验收口径。

## 七 风险与应对

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| 与 HolmesGPT/Robusta 同质化 | 用户说“已有开源方案” | 强调离线历史包、证据引用、可复现；不拼聊天 |
| 安装后不用 | 激活率 <20% | 优化 5 分钟示例；首次诊断零配置；真实事故模板 |
| 模型成本/隐私 | 用户拒绝联网 | 默认离线；Ollama；预算/降级 |
| 企业版边界争议 | “为什么单次诊断要付费” | 单次永远免费；企业卖团队/治理/部署 |
| 维护负担 | issue 堆积/版本漂移 | 限定 K8s/数据源；schema 冻结；自动化 golden |
| 指标造假/虚荣 | 只报 Star | 以安装→激活→重复→试点漏斗为周报 |
| 安全事件 | 日志含 token | 导入即扫描；validate 拒绝；报告二次校验 |

## 九 90 天后的决策点

| 观察 | 决策 |
| --- | --- |
| 激活 ≥30%，重复 ≥25%，≥10 合格试点 | 加投企业版/招聘 |
| 安装高但激活低 | 先修首次体验，不扩功能 |
| 激活高但无试点 | 检查企业需求/定价/安全门槛 |
| 有试点但单次诊断被当免费替代 | 强化团队库/审计/评测价值，不阉割 CLI |
| 10 次合格演示仍无接入 | 按商业方案停投条件复盘，不追加功能 |

**最终判断标准**：不是 Star，而是“装得下、用得上、会再用、有人愿意为团队化付费”。

## 十 口径决策记录

- golden 基线 12 个（五类×2 + 缺失 + 注入）；

- `--offline` 默认 false，且与 `--model` 互斥；
- `--max-evidence` 默认 200，M1 实现；
- go.mod 最低 Go 1.24，CI 用 1.26；
- 外部商业方案文档只作外部引用，不随 OSS 发布。

M1 实现层的口径（证据字段/content_ref、退出码优先级、脱敏三模式、schema 校验方式、golden 布局、import 产物形态、CI 门禁）见 [ADR-003 M1 实现口径](adr/ADR-003-M1实现口径.md)。
M2 模型与评测的口径（provider 协议、配置/密钥、降级、预算/轮次、输出校验与注入防护、eval 契约）见 [ADR-004 M2 实现口径](adr/ADR-004-M2实现口径.md)。
