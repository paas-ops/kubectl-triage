**轻量 Kubernetes 事故诊断 CLI（开源版）**

| 项 | 内容 |
| --- | --- |
| 版本 | v0.1（立项稿） |

## 一 背景与定位

CloudOps Agent 的商业方案明确：开源方案降低基础诊断门槛，收费应来自**部署效率、权限治理、
持续评估与事故协作**，而不是模型调用本身。与此同时，HolmesGPT、Robusta 等开源项目已经
覆盖“让模型解释日志”的一部分需求；差异化不能是“再做一个会聊天的 kubectl”。

本项目的切口是：

> **把一次历史故障变成可复现、可追溯、可评审的本地诊断报告。**
> 不要求先接入平台、不要求把生产日志上传到 SaaS、不要求先买订阅。

### 1.1 产品承诺

开发者拿到一份脱敏的事故证据包（或从现有监控/工单系统导出），在本地执行一条命令：

```bash
kubectl triage analyze ./incidents/2026-10-12-checkout-oom
```

在 30 秒内（离线规则模式）或 5 分钟内（可选模型模式）得到：

- 事故摘要与影响范围；
- 按时间排列的证据时间线（来源、观察时间、采集时间、查询/文件引用）；
- Top 3 候选根因，每条都引用证据，并显示反证与置信分层；
- 缺失证据与下一步检查建议；
- 只读修复建议（明确标注“不自动执行”）；
- Markdown 报告 + 机器可读 JSON。

### 1.2 目标

1. 让没有平台账号的开发者，**5 分钟内完成第一次本地诊断**。
2. 让历史事故可以脱离原集群被复盘：证据包可存档、可分享、可回归。
3. 用“证据引用 + 反证 + 缺失说明”建立可信度，而不是用模型口吻。
4. 成为企业版的自然入口：单次诊断用顺手后，团队才需要事故库、评测、审计与私有部署。

### 1.3 非目标

- 不做生产自动修复、不做 `kubectl apply/delete/exec`、不读取 Secret。
- 不做多租户 SaaS；开源 CLI 默认不联网、不上传证据。
- 不做“万能 K8s 助手”；MVP 只覆盖五类故障：CrashLoopBackOff、OOMKilled、
  ImagePullBackOff、Pending、发布回归。
- 不在没有评测数据时宣称准确率；不以 GitHub Star 作为成功指标。
- 不把企业版的团队库/审计/评测能力伪装成开源功能。

## 二 用户与场景

| 用户 | 场景 | 成功标准 |
| --- | --- | --- |
| 应用开发者 | 收到告警，本地只有 `kubectl` 输出和几段日志 | 不登平台就能得到有证据的根因草稿 |
| 值班 SRE | 事故后复盘，需要把证据和结论留档 | 一份可审阅的 Markdown/JSON 报告 |
| 平台工程师 | 评估诊断工具是否值得团队采购 | 用自己脱敏的 10 起历史事故复跑 |
| 安全/合规 | 生产日志不能出域 | 离线模式可运行，证据包哈希可核验 |
| 企业购买者 | 团队需要共享事故库、评测和审计 | 从 CLI 试点升级到企业版 |

### 2.1 典型旅程

1. `kubectl triage init ./incidents/checkout-oom` 生成事故包骨架。
2. 从 Alertmanager/工单/`kubectl`/Prometheus/Loki 导出数据，放入包内。
3. `kubectl triage validate ./incidents/checkout-oom` 检查 schema、时间戳、敏感字段。
4. `kubectl triage analyze ... --offline` 本地规则诊断；或 `--model ollama` 使用本地模型。
5. 阅读 `report.md`，用 `--format json` 接入自己的工单/知识库。
6. 可选：`kubectl triage push` 把**脱敏后的报告**同步到企业事故库（需显式配置）。

## 三 开源版 vs 企业版

| 能力 | 开源 CLI（免费） | 企业版（CloudOps Agent） |
| --- | --- | --- |
| 单次本地诊断 | ✅ 不限次数，一次一个事故包 | ✅ |
| 离线规则分析 | ✅ | ✅ |
| 可选本地/自带模型 | ✅（用户自己的 key/Ollama） | ✅ + 统一模型网关/配额 |
| Markdown/JSON 报告 | ✅ | ✅ |
| 团队事故库/检索/标签/负责人 | ❌ | ✅ |
| 批量回放与评测集管理 | 本地单机脚本（可选） | ✅ 版本对比、盲测、质量看板 |
| 审计（谁在何时看了什么、模型/版本） | ❌ | ✅ 不可变审计、导出 |
| SSO/RBAC/多租户 | ❌ | ✅ |
| 私有化/专有网络/离线部署 | ❌ | ✅ 交付与支持 |
| 工单/知识库/告警平台集成 | 基础导入 | ✅ 双向同步与治理 |
| 支持 | 社区 | 商业 SLA |

**边界原则**：开源版永远可以完成“一次完整诊断”；企业版不通过故意阉割单次诊断来收费，
而是通过团队协作、治理、评估与部署效率收费。这样既符合商业方案，也避免 open-core 反弹。

### 3.1 “免费单次诊断”的定义

- 免费版**不限制诊断次数**，但**一次命令只处理一个事故包**；
- 不提供账号、云端存储、团队共享、批量评测、审计或私有部署支持；
- 不强制遥测；匿名使用统计必须显式 opt-in；
- 模型费用由用户自己的 key/本地模型承担。

## 四 CLI 规格

### 4.1 命令面

```text
kubectl triage init <dir>                 生成事故包骨架与示例
kubectl triage import <source> <dir>      从 alertmanager/kubectl/prometheus/loki 导入
kubectl triage validate <dir>             校验 schema、时间、脱敏与证据完整性
kubectl triage analyze <dir> [flags]      诊断，输出 report.md / report.json
kubectl triage report <dir>               重新渲染已有报告（不重新分析）
kubectl triage eval <dir>                 本地评测（golden cases，可选）
kubectl triage push <dir>                 推送到企业控制平面（显式配置）
kubectl triage version                    版本/构建信息
```

`analyze` 关键参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--offline` | false | 禁止所有网络；使用确定性规则分析 |
| `--model` | `none` | `none` / `ollama` / `openai-compatible` |
| `--model-url` / `--model-name` | — | 兼容 OpenAI 的本地/自建网关 |
| `--format` | `md` | `md` / `json` / `both` |
| `--out` | 包内 `report.*` | 输出路径 |
| `--max-evidence` | 200 | 证据上限，防大包拖垮 |
| `--redact` | `strict` | `strict` / `standard` / `off`（不建议） |
| `--fail-on-missing` | false | 缺关键证据时退出码 2（CI 可用） |

### 4.2 退出码

| 码 | 含义 |
| --- | --- |
| 0 | 成功，报告已生成 |
| 1 | 输入/配置错误 |
| 2 | 证据不足，报告带缺失项（可用 `--fail-on-missing` 触发） |
| 3 | 模型/网络失败，已回退离线规则（报告标注降级） |
| 4 | 安全校验失败（疑似 Secret/越权数据） |

### 4.3 首次运行体验

- 无账号、无登录、无云端依赖；
- `init` 生成一个 5 分钟可跑通的示例事故包；
- `analyze` 默认离线规则，确保“第一次就有结果”；
- 输出末尾给出下一步：如何导入真实事故、如何启用本地模型、如何申请企业试点；
- 错误信息给出可执行修复，不用“Oops”。

## 五 事故包规范（输入契约）

一个事故包是一个目录，最小结构：

```text
incidents/2026-10-12-checkout-oom/
├── incident.yaml          # 必填：事故元数据
├── alert.json             # 可选：Alertmanager 原始告警
├── k8s/
│   ├── events.json        # kubectl get events -o json
│   ├── pods.yaml          # kubectl get pods -o yaml（已裁剪）
│   └── deployments.yaml   # 可选
├── metrics/
│   └── memory.json        # Prometheus query_range 结果
├── logs/
│   └── checkout-api.log   # 已脱敏日志摘录
├── changes/
│   └── rollout.json       # 可选：发布/镜像/commit 信息
├── runbook.md             # 可选：团队 runbook 摘录
└── notes.md               # 可选：值班记录
```

`incident.yaml` 必填字段：

```yaml
id: 2026-10-12-checkout-oom
alertname: KubePodCrashLooping
severity: critical
cluster: prod-shanghai
namespace: checkout
workload: checkout-api
observed_at: 2026-10-12T09:14:00Z
collected_at: 2026-10-12T09:20:00Z
source: alertmanager
```

### 5.1 证据条目

每条证据统一为：

```json
{
  "id": "ev-001",
  "source": "k8s.events",
  "observed_at": "2026-10-12T09:14:00Z",
  "collected_at": "2026-10-12T09:20:00Z",
  "summary": "Pod checkout-api-7d9f OOMKilled，exitCode=137",
  "content_ref": "k8s/events.json#items/3",
  "query": "kubectl get events -n checkout -o json",
  "redaction": "strict/r1",
  "sha256": "…"
}
```

约束：

- 观察时间与采集时间必须分开；时钟偏差超过 9 秒在报告中标记。
- 过期证据（默认 >15 分钟）标为 stale，不得作为高置信结论的唯一依据。
- 每条结论必须引用证据 id；引用不存在/越界的证据视为报告生成失败。
- 证据包默认只存摘录，不存 Secret、完整环境变量、完整 ConfigMap 正文。

## 六 诊断输出契约

`report.json` 顶层：

```json
{
  "schema_version": "1.0",
  "incident": {"id": "...", "alertname": "...", "cluster": "...", "namespace": "..."},
  "generated_at": "...",
  "mode": "offline|model",
  "degraded": false,
  "summary": "...",
  "evidence": [{"id": "ev-001", "source": "...", "observed_at": "...", "stale": false}],
  "hypotheses": [
    {
      "rank": 1,
      "statement": "容器内存 limit 过低导致 OOMKilled",
      "confidence": "high|mid|low",
      "evidence_ids": ["ev-001", "ev-004"],
      "contradictions": [{"evidence_id": "ev-007", "note": "同期节点内存充足"}]
    }
  ],
  "missing_data": [{"source": "prometheus", "reason": "查询超时", "next_step": "..."}],
  "recommended_checks": ["..."],
  "suggested_fix": "只读建议，不自动执行",
  "limitations": ["..."],
  "versions": {"cli": "...", "rules": "...", "model": "..."}
}
```

硬性要求：

- `hypotheses` 最多 3 条；每条至少 1 条有效证据引用。
- 证据不足时允许 `hypotheses: []`，但必须给出 `missing_data` 与下一步。
- `suggested_fix` 只描述建议，不生成可执行脚本、不调用集群写接口。
- 报告不包含 Secret、token、完整环境变量；`validate` 与 `analyze` 双重检查。
- Markdown 由 JSON 渲染，二者内容一致；JSON 为稳定接口。

## 七 分析引擎

### 7.1 离线规则（默认）

- 基于五类故障的确定性规则：事件原因、容器状态、镜像拉取错误、调度条件、发布差异。
- 规则只消费证据包，不访问集群。
- 输出固定、可快照测试；同一输入必须得到同一报告（除时间戳/版本）。
- 规则版本写入报告，便于回溯。

### 7.2 可选模型

- 支持 OpenAI 兼容接口与 Ollama；默认不启用。
- 模型只做“基于已给证据的归纳”，不新增工具、不访问 URL、不执行命令。
- 模型输出必须通过 JSON schema 校验；引用不存在证据 → 整份报告失败或降级规则。
- 预算：默认单次 ≤ $1 / ≤ 3 轮；超预算降级规则并标注。
- 网络仅在显式 `--model` 时启用；`--offline` 下任何网络调用都视为失败。

### 7.3 降级

- 模型不可用/超时/输出不合规 → 规则报告 + `degraded: true` + 原因。
- 证据缺失 → 允许部分报告，但不得编造根因。
- 输入过大 → 按证据上限裁剪，明确列出被裁剪项。

## 八 安全与隐私

| 风险 | 要求 |
| --- | --- |
| Secret/凭据 | 不读取 Secret；导入时扫描 token/密钥模式；`validate` 失败则拒绝分析 |
| 数据出域 | 默认零网络；模型调用需显式参数；报告不含原始大对象 |
| 越权证据 | 证据引用必须来自包内；跨包引用拒绝 |
| 误操作 | 只读；不生成 `kubectl apply/delete/exec`；不自动执行修复 |
| 供应链 | Release 提供 SHA256、SBOM、签名；Homebrew 校验 |
| 遥测 | 默认关闭；opt-in 匿名事件；不采集事故内容、命名空间、集群名 |

## 十 成功指标（不以 Star 为核心）

### 10.1 指标定义

| 指标 | 定义 | 采集方式 |
| --- | --- | --- |
| 实际安装 | 去重后的 Release/Homebrew/容器安装 | Release 下载、Homebrew analytics、镜像拉取（粗粒度） |

| 企业试点请求 | 来自 CLI/文档/评测页的合格申请 | 表单 UTM + 资格访谈 |
| Star（参考） | 社区关注度 | GitHub，仅作辅助，不作为目标 |

### 10.2 90 天目标（假设，需验证）

| 指标 | 目标 |
| --- | --- |
| 实际安装 | ≥1,000 |
| 激活率 | ≥30% |

## 十一 MVP 验收标准

1. `kubectl triage init` + `analyze --offline` 在 5 分钟内跑通示例。
2. 五类故障各至少 2 个 golden 事故包；报告含证据引用、反证/缺失、只读建议。
3. 离线模式零网络请求；`--offline` 下模型/网络调用必须失败并说明。
4. 证据包中植入 token/Secret 模式 → `validate` 拒绝；报告不含敏感串。
5. 注入恶意日志（要求外传/执行命令）→ 零越权、零外传 URL。
6. 同一输入重复运行，除时间戳/版本外输出一致。
7. `report.json` 通过 schema 校验；Markdown 与 JSON 内容一致。
8. 单二进制在 macOS/Linux 可运行；Release 有 SHA256 与 SBOM。
9. 本地 eval 种子集全部通过；正式 100 例盲测作为企业版/发布门槛另行管理。
10. 首次运行文档可在 10 分钟内让新用户完成一次真实事故诊断。

## 十二 依赖、风险与待决

### 依赖

- 现有 CloudOps Agent 的证据/报告 schema（抽取为 Apache-2.0 公共包或独立定义）。
- 五类故障 runbook 的公开版本；企业 runbook 不进入开源仓库。
- 至少 10 起脱敏历史事故用于 golden 测试；正式评测需两名 SRE 标注。

### 风险

| 风险 | 应对 |
| --- | --- |
| 与 HolmesGPT/Robusta 同质化 | 聚焦“离线历史事故包 + 证据引用 + 可复现”，不拼聊天 |
| 模型成本/隐私 | 默认离线；模型 opt-in；预算与脱敏 |
| 开源版被当免费企业版 | 明确边界；团队库/审计/评测只在企业版 |
| 维护负担 | 限定 K8s 版本/数据源；schema 稳定；自动化 golden |
| 指标失真 | 不以 Star 为 KPI；安装/激活/重复/试点四层漏斗 |

### 待决

1. 正式名称与包名（GitHub/Homebrew/镜像/商标）。
2. 证据 schema 是独立仓库还是从 CloudOps Agent 抽取公共包。
3. 是否在 OSS 版提供本地 eval（建议提供，但不含团队评测服务）。
4. 企业版同步协议：只同步报告/证据哈希，还是可选同步脱敏证据包。
5. 首发是否支持 Windows（建议 v0.2）。
